🌳 What is a Binary Search Tree? Foundation

A Binary Search Tree (BST) is a tree where every node follows one golden rule:

The BST Rule: For any node → everything on the LEFT is smaller, and everything on the RIGHT is larger. This holds for every single node, recursively.
⬅️
Left = SmallerAll values in the left subtree are less than the node.
➡️
Right = LargerAll values in the right subtree are greater than the node.
⚡
Fast SearchEach step throws away half the tree → O(log n).
🔗
Same Idea as Binary SearchA BST is binary search "frozen" into a tree structure.

💡 The intuition (read this once, keep it forever)

The "hot or cold" number game: A friend picks a number 1–100. You guess 50. They say “higher.” Instantly you throw away 1–50 forever and guess 75. A BST is that game built into a structure — every node is a guess, going left means “lower,” going right means “higher.”

Why it beats a normal list: in a plain list you'd check items one by one. In a BST, every node you visit lets you ignore an entire subtree — half the remaining data — so searching a balanced tree of a million nodes takes only ~20 hops. Same power as binary search, kept alive as you insert and delete.

start at root→ target < node? go left ⬅️/ target > node? go right ➡️→ equal? ✅ found
🔒 Lifetime takeaway: “Every node is a yes/no gate — smaller goes left, larger goes right, and half the tree vanishes each step.”

🔑 Common Observations in Binary Search Core

Every binary search problem is a remix of these ideas. Master them once and all the problems below become easy.

🎚️
Two Pointers: lo & hiThey define the search window. The answer always lives between them.
📍
Safe midUse mid = lo + (hi - lo) / 2 to avoid integer overflow.
✂️
Halve every stepDiscard the half that cannot contain the answer → O(log n).
🧭
Monotonic conditionYou need a "yes/no" that flips only once across the range.
🔁
Don't stop earlyFor first/last occurrence, keep searching even after a match.
⚖️
Loop invariantwhile (lo <= hi) vs lo < hi changes the boundary logic.

💡 The intuition (read this once, keep it forever)

The dictionary trick: To find a word in a 1000-page dictionary you don't flip page by page. You open the middle. Too far ahead? Rip out the second half. Too far back? Rip out the first half. Open the middle of what's left. In ~10 opens you land on any word. That is binary search.

Why it works: the array is sorted, so the middle value tells you which half the answer cannot be in. Throwing away half every step means 1,000,000 items take only ~20 comparisons — that's the magic of O(log n).

1. mid = middle→ 2. equal? ✅ done→ 3. mid too small? go right→ 4. mid too big? go left→ 5. repeat
🔒 Lifetime takeaway: “Look at the middle, throw away the half that can't contain the answer, repeat.”

int binarySearch(int[] a, int target) {
  int lo = 0, hi = a.length - 1;
  while (lo <= hi) {
    int mid = lo + (hi - lo) / 2;   // safe mid
    if (a[mid] == target) return mid;   // found
    else if (a[mid] < target) lo = mid + 1; // go right
    else hi = mid - 1;                 // go left
  }
  return -1; // not present
}

🎯 First & Last Occurrence Duplicates

In an array with duplicates, find the first and last index of a target. Trick: when you find it, don't stop — keep shrinking toward the side you want.

💡 The intuition (read this once, keep it forever)

The name in a phone book: Imagine 100 people all named “Sharma”. You found a Sharma — great, but where does the block start and end? When you land on a Sharma, you don't celebrate and stop. You write down the page and keep flipping backward to find the very first one (or forward for the very last).

The one insight: a normal binary search stops at the first match. Here the match is not the end — it's a candidate. Save it, then deliberately keep going toward the side you want. That single change (don't stop, keep going left OR right) turns one search into a boundary finder.

match found→ save mid as answer→ FIRST: hi = mid-1 ⬅️/ LAST: lo = mid+1 ➡️
🔒 Lifetime takeaway: “On a match, don't stop — save it and squeeze toward the edge you want.”
Finding 🔎 5 in [1, 3, 5, 5, 5, 5, 8, 9]. First we hunt the leftmost 5, then the rightmost 5.
Press play to find the first and last position of 5.
🐢 🐇
🧠
Never forget: Found a match? For the first occurrence move hi = mid - 1 (keep looking left). For the last occurrence move lo = mid + 1 (keep looking right). Always store mid as your best answer before moving.
int findBound(int[] a, int t, boolean first) {
  int lo = 0, hi = a.length - 1, ans = -1;
  while (lo <= hi) {
    int mid = lo + (hi - lo) / 2;
    if (a[mid] == t) {
      ans = mid;                 // record candidate
      if (first) hi = mid - 1; // keep going LEFT
      else      lo = mid + 1; // keep going RIGHT
    } else if (a[mid] < t) lo = mid + 1;
    else hi = mid - 1;
  }
  return ans;
}

🔄 Search in a Rotated Sorted Array Classic

A sorted array was rotated at some pivot, e.g. [4,5,6,7,0,1,2]. Still find the target in O(log n)! The trick: one half is always sorted — figure out which, then decide where the target lives.

💡 The intuition (read this once, keep it forever)

The cut deck of cards: Take a sorted deck and “cut” it once — the top part moves to the bottom. The deck looks scrambled, but here's the secret: no matter where you cut, at least one half is still perfectly in order. Stand at the middle card and look left and right — one side always climbs smoothly.

The one insight: you can't trust the whole array anymore, but you can always trust the sorted half. So: find the sorted half, check “is my target inside its clean min…max range?” If yes, dive into it. If no, the answer must be in the messy half — go there. Every step still kills half the array.

a[lo] ≤ a[mid]?→ left half is sorted→ target in [a[lo], a[mid])? go left→ else go right
🔒 Lifetime takeaway: “One half is always sorted — decide using the half you can trust.”
Searching 🔎 0 in [4, 5, 6, 7, 0, 1, 2].
Press play to search the rotated array.
🐢 🐇
🧠
Never forget: Check if left half is sorted (a[lo] <= a[mid]). If yes and target is inside [a[lo], a[mid]) → go left, else go right. Otherwise the right half is sorted → mirror the logic. Always lean on the sorted half.
int searchRotated(int[] a, int t) {
  int lo = 0, hi = a.length - 1;
  while (lo <= hi) {
    int mid = lo + (hi - lo) / 2;
    if (a[mid] == t) return mid;
    if (a[lo] <= a[mid]) {          // LEFT half sorted
      if (a[lo] <= t && t < a[mid]) hi = mid - 1;
      else lo = mid + 1;
    } else {                        // RIGHT half sorted
      if (a[mid] < t && t <= a[hi]) lo = mid + 1;
      else hi = mid - 1;
    }
  }
  return -1;
}

⛰️ Peak Element Direction

A peak is an element greater than its neighbors. Even in an unsorted array you can find a peak in O(log n) by always walking uphill.

💡 The intuition (read this once, keep it forever)

The mountain hiker in the fog: You're on a mountain range in thick fog — you can only feel the ground under your foot and the slope beside you. Rule: always step toward the higher side. If you keep walking uphill, you must eventually reach a summit — you can't climb forever, the range ends. That summit is your peak.

The one insight: the array doesn't need to be sorted! If the neighbor on the right is higher, a peak is guaranteed somewhere to the right (you're going up, and it can't rise forever). So move that way. This “follow the higher slope” rule squeezes the two pointers onto a peak in O(log n).

a[mid] < a[mid+1]?→ uphill on the right → lo = mid+1 ➡️/ else peak here/left → hi = mid ⬅️
🔒 Lifetime takeaway: “Always walk toward the higher neighbor — uphill always ends at a peak.”
Array [1, 3, 20, 4, 1, 0]. If a[mid] < a[mid+1], a peak must exist to the right — go there. Otherwise go left.
Press play to climb toward a peak.
🐢 🐇
🧠
Never forget: Always walk toward the higher neighbor — uphill always leads to a peak. a[mid] < a[mid+1] ? go right (lo = mid+1) : go left (hi = mid). The two pointers collapse onto a peak.
int findPeak(int[] a) {
  int lo = 0, hi = a.length - 1;
  while (lo < hi) {
    int mid = lo + (hi - lo) / 2;
    if (a[mid] < a[mid + 1]) lo = mid + 1; // uphill → right
    else hi = mid;                            // downhill → left
  }
  return lo; // lo == hi → a peak index
}

♻️ Find the Repeated Element Pigeonhole

Given n + 1 numbers in range [1..n], exactly one value repeats. Find it in O(log n) time and O(1) space by binary searching on the answer's value, not the index.

💡 The intuition (read this once, keep it forever)

The pigeonhole / hotel rooms: You have rooms numbered 1 to 4, but 5 guests checked in. By common sense, one room must be shared — that's the duplicate. Now play “20 questions” on the value: “Is the duplicate ≤ 2?” Count how many guests have a room number ≤ 2. If there are more guests than rooms in that lower range, the duplicate is hiding down there.

The mind-bending insight: here you binary search on the value (1..n), not on array positions. For any midpoint value m, if the count of numbers ≤ m is greater than m, then too many numbers are crammed into a small range → the duplicate must be ≤ m. Otherwise it's above m. That's the pigeonhole principle turned into a search.

pick value mid→ count how many ≤ mid→ count > mid? dup is ≤ mid → hi = mid/ else lo = mid+1
🔒 Lifetime takeaway: “Search the value range, not indices — too many numbers in a range means the duplicate lives there.”
Array [1, 3, 4, 2, 2], range = 1..4. We binary search the value range and count how many numbers are ≤ mid.
Press play. We search values 1..4, not indices.
🐢 🐇
🧠
Never forget: Binary search on values 1..n. Count how many array elements are ≤ mid. If that count > mid, the duplicate hides in the lower half → hi = mid; else lo = mid + 1. This is the pigeonhole principle in action.
int findDuplicate(int[] a) {
  int lo = 1, hi = a.length - 1; // value range 1..n
  while (lo < hi) {
    int mid = lo + (hi - lo) / 2;
    int count = 0;
    for (int x : a) if (x <= mid) count++;
    if (count > mid) hi = mid;   // dup in lower half
    else lo = mid + 1;         // dup in upper half
  }
  return lo; // the repeated value
}

🧩 Single Element in a Sorted Array Parity

Every element appears exactly twice except one that appears once. Find that loner in O(log n).

💡 The intuition (read this once, keep it forever)

The broken pair pattern: Line up socks in matching pairs: positions (0,1), (2,3), (4,5)… Before the odd sock, every pair sits neatly — the first of a pair lands on an even index. After the loner, the pairing shifts by one and breaks. The loner is exactly where the neat pattern first breaks.

The one insight: take an even index mid. If a[mid] == a[mid+1], the loner is to the right (pairs are still intact here). If not, the loner is at or to the left. That yes/no flips exactly once → perfect for binary search.

force mid even→ a[mid]==a[mid+1]? pairs ok → go right/ else loner is here/left → go left
🔒 Lifetime takeaway: “At an even index, a happy pair means the loner is to the right; a broken pair means it's at or to the left.”
Array [1,1,2,3,3,4,4,8,8] — the single element is 🎯 2.
Press play to find the lonely element.
🐢 🐇
🧠
Never forget: Keep mid even. a[mid]==a[mid+1] → lo = mid+2, else hi = mid. The loner breaks the even-pairing.
int singleElement(int[] a) {
  int lo = 0, hi = a.length - 1;
  while (lo < hi) {
    int mid = lo + (hi - lo) / 2;
    if (mid % 2 == 1) mid--;      // make mid even
    if (a[mid] == a[mid + 1]) lo = mid + 2; // pairs intact → right
    else hi = mid;                     // broken → here or left
  }
  return a[lo];
}

📈 Binary Search on a Monotonic Function The Meta-Pattern

The master skill: when a condition is false, false, …, true, true (it flips only once), binary search finds the exact flip point — even without an array!

💡 The intuition (read this once, keep it forever)

The light switch on a dimmer: Slide a dimmer from dark to bright. There's exactly one point where “too dark” becomes “bright enough.” You don't test every millimeter — you jump to the middle, ask “bright enough?”, and slide toward the boundary. Binary search doesn't need numbers in a list; it needs a question whose answer flips once.

The unlock: stop thinking “search an array.” Start thinking “search the answer space for the boundary of a monotonic check(x).” Square roots, cows, books, Koko-bananas — all of them are secretly this. Find the first true (or last true).

define check(x): monotonic bool→ check(mid) true? answer ≤ mid → hi = mid/ else lo = mid+1
🔒 Lifetime takeaway: “If a yes/no flips exactly once, binary search finds the flip — arrays optional.”
Predicate over x = 0..11: check(x) = (x >= 7). We hunt the first TRUE.
F = not yet, T = condition holds. Find the first T.
🐢 🐇
🧠
Never forget: check(mid) true → the answer can't be bigger, so hi = mid. False → lo = mid+1. When lo==hi you've found the boundary.
int firstTrue(int lo, int hi) {
  while (lo < hi) {
    int mid = lo + (hi - lo) / 2;
    if (check(mid)) hi = mid;   // boundary at mid or left
    else lo = mid + 1;        // boundary to the right
  }
  return lo; // first x with check(x)==true
}

√ Integer Square Root Answer Search

Compute floor(√N) without a math library — binary search the answer.

💡 The intuition (read this once, keep it forever)

Guess the side of a square: You have N tiles and want the biggest square you can build. Guess a side s. Too many tiles needed (s² > N)? The side is smaller. Fits (s² ≤ N)? Maybe you can go bigger. You're playing the number-guessing game on the side length.

Why binary search fits: the function s² is monotonically increasing. So “is s² ≤ N?” is TTT…FFF — a perfect monotonic predicate. We want the last s that still fits.

guess side mid→ mid² ≤ N? record it, go bigger/ else go smaller
🔒 Lifetime takeaway: “sqrt = biggest side whose square still fits — guess the side, not the root.”
Finding floor(√50) by searching sides 1..16 (we cap the window since 16² > 50). Answer = 🎯 7 (7²=49 ≤ 50 < 64=8²).
Searching side length in 1..50 for N=50.
🐢 🐇
🧠
Never forget: mid*mid ≤ N → save mid, lo = mid+1 (try larger). Else hi = mid-1. Use long for mid*mid to avoid overflow.
int sqrtFloor(int n) {
  long lo = 0, hi = n, ans = 0;
  while (lo <= hi) {
    long mid = lo + (hi - lo) / 2;
    if (mid * mid <= n) { ans = mid; lo = mid + 1; } // fits, try bigger
    else hi = mid - 1;                             // too big
  }
  return (int) ans;
}

3️⃣ Kth Smallest in an Array Value Search

Find the k-th smallest value using binary search on the value range (no sorting needed).

💡 The intuition (read this once, keep it forever)

The exam rank cutoff: You want the score of the 3rd-lowest student. Guess a cutoff score. Count how many students scored ≤ that cutoff. Too few (< 3)? Raise the cutoff. Enough (≥ 3)? Lower it to find the tightest value. You're binary searching the score, and “count ≤ x” is your compass.

The one insight: count(≤ x) only grows as x grows — monotonic! The smallest x whose count reaches k is exactly the k-th smallest value. This idea scales to matrices and two arrays too.

guess value mid→ count(≤ mid) ≥ k? shrink right: hi = mid/ else lo = mid+1
🔒 Lifetime takeaway: “The k-th smallest is the smallest value with at least k elements ≤ it.”
Array [7,10,4,3,20,15], k = 🎯 3 → answer 7. We search values in [3..20].
Binary searching the value range, counting elements ≤ mid.
🐢 🐇
🧠
Never forget: Binary search on value. count(≤ mid) ≥ k → hi = mid; else lo = mid+1. Answer = lo.
int kthSmallest(int[] a, int k) {
  int lo = min(a), hi = max(a);
  while (lo < hi) {
    int mid = lo + (hi - lo) / 2, count = 0;
    for (int x : a) if (x <= mid) count++;
    if (count >= k) hi = mid;  // enough small ones → shrink
    else lo = mid + 1;
  }
  return lo;
}

🔗 Kth Smallest in Two Sorted Arrays Partition

Two sorted arrays, find the k-th smallest across both — in O(log(min(n,m))) using a smart partition.

💡 The intuition (read this once, keep it forever)

Cutting two ribbons: Lay two sorted ribbons side by side. Make a single cut through both so that exactly k numbers fall on the left. A cut is “perfect” when the biggest number on the left is ≤ the smallest on the right — the two halves interlock cleanly. Slide the cut using binary search until it clicks.

The one insight: only binary-search the cut position in the smaller array; the cut in the second array is forced (k − cutA). Check the four boundary values L1,R1,L2,R2: if L1 > R2 the cut in A is too far right; if L2 > R1 it's too far left. When both interlock, the answer is max(L1, L2).

cut smaller array at cutA→ cutB = k − cutA→ L1≤R2 & L2≤R1? done/ else slide the cut
🔒 Lifetime takeaway: “Search the cut, not the values — a perfect cut puts k on the left with both halves interlocking.”
A = [2,3,6,7,9], B = [1,4,8,10], k = 🎯 5 → the 5th smallest is 6.
Array A
Array B
Sliding the partition to place exactly k=5 elements on the left.
🐢 🐇
🧠
Never forget: Binary search cutA in the smaller array; cutB = k − cutA. Compare L1,R1,L2,R2. L1 > R2 → move cut left; L2 > R1 → move cut right; else answer = max(L1,L2).
// a is the shorter array; find k-th smallest (1-indexed)
int kthTwo(int[] a, int[] b, int k) {
  int lo = max(0, k - b.length), hi = min(k, a.length);
  while (lo <= hi) {
    int cutA = lo + (hi - lo) / 2, cutB = k - cutA;
    int L1 = cutA==0? MIN : a[cutA-1];
    int R1 = cutA==a.length? MAX : a[cutA];
    int L2 = cutB==0? MIN : b[cutB-1];
    int R2 = cutB==b.length? MAX : b[cutB];
    if (L1 <= R2 && L2 <= R1) return max(L1, L2);
    else if (L1 > R2) hi = cutA - 1;
    else lo = cutA + 1;
  }
  return -1;
}

🔢 Kth Smallest in a Sorted Matrix Staircase Count

Rows and columns are sorted. Find the k-th smallest value by binary searching on value + a clever L-shaped count.

💡 The intuition (read this once, keep it forever)

The staircase walk: Stand at the bottom-left corner of the grid. If the current cell ≤ your guess, the whole column below-and-here is ≤ it — count it and step right. If it's too big, step up. In one staircase walk (n+m steps) you count everything ≤ your guess. No need to touch every cell.

The one insight: just like the array version, binary search on the value from matrix[0][0] to matrix[n-1][m-1]. The only trick is counting “how many ≤ mid” fast — the sorted rows/cols let you do it with a single L-shaped sweep instead of O(n²).

guess value mid→ staircase-count ≤ mid→ count ≥ k? hi = mid/ else lo = mid+1
🔒 Lifetime takeaway: “Binary search the value; count ≤ mid with a bottom-left staircase walk.”
Matrix rows & cols sorted. k = 🎯 8. Watch the staircase count light up cells ≤ mid.
Binary searching value; green = counted (≤ mid).
🐢 🐇
🧠
Never forget: lo = matrix[0][0], hi = matrix[n-1][m-1]. Count ≤ mid from bottom-left (right if ≤, up if >). count ≥ k → hi = mid, else lo = mid+1.
int kthInMatrix(int[][] m, int k) {
  int n = m.length, lo = m[0][0], hi = m[n-1][n-1];
  while (lo < hi) {
    int mid = lo + (hi - lo) / 2, count = 0;
    int r = n - 1, c = 0;              // bottom-left
    while (r >= 0 && c < n) {
      if (m[r][c] <= mid) { count += r + 1; c++; } // column counted
      else r--;
    }
    if (count >= k) hi = mid;
    else lo = mid + 1;
  }
  return lo;
}

📈 Maximize K — Binary Search on the Answer Maximize

The mirror of "first true": when feasibility is true, true, …, false, find the largest value that still works.

💡 The intuition (read this once, keep it forever)

The heaviest backpack you can still carry: Small loads are easy (feasible), huge loads are impossible. Somewhere is the heaviest load you can still manage. You don't try every weight — you guess the middle: "can I carry this?" If yes, get greedy and try heavier; if no, back off. You're maximizing under a monotonic "can I?" test.

The one insight: "maximize the minimum" or "largest feasible K" problems all share this skeleton — feasible(x) is TTT…FFF. For a maximize, when feasible(mid) is true you move up (lo = mid+1) and remember mid; when false you move down. This is the engine behind cows and books below.

guess K = mid→ feasible(mid)? save + go higher: lo = mid+1/ else hi = mid−1
🔒 Lifetime takeaway: “Maximize = find the LAST true. Feasible? reach higher. Not? pull back.”
Feasibility over K = 0..11: feasible(K) = (K <= 7). We hunt the largest feasible K = 7.
T = feasible, F = too much. Find the last T.
🐢 🐇
🧠
Never forget: Maximize → feasible(mid) true means go higher (lo = mid+1, record mid); false means hi = mid-1. Minimize is the mirror image.
int maximizeK(int lo, int hi) {
  int ans = lo;
  while (lo <= hi) {
    int mid = lo + (hi - lo) / 2;
    if (feasible(mid)) { ans = mid; lo = mid + 1; } // reach higher
    else hi = mid - 1;                             // pull back
  }
  return ans;
}

🐄 Place the Cows (Aggressive Cows) Maximize Min

Put C cows into stalls so the minimum distance between any two is as large as possible.

💡 The intuition (read this once, keep it forever)

Grumpy cows need space: Cows fight if too close. You want to spread C cows so the closest pair is as far apart as possible. Guess a minimum gap d: greedily place a cow in the first stall, then skip ahead until the next stall is ≥ d away. Could you seat all cows? If yes, be greedier — try a bigger gap. If no, shrink the gap.

The one insight: "can we place all cows with gap ≥ d?" is monotonic — if a big gap works, every smaller gap works too (TTT…FFF). So binary search on the answer d. This is the classic maximize-the-minimum template.

sort stalls→ guess gap d→ greedily seat cows ≥ d apart→ all seated? go bigger, else smaller
🔒 Lifetime takeaway: “Binary search the minimum gap; greedily place and ask ‘did everyone fit?’”
Stalls [1,2,4,8,9], C = 3 cows → best minimum distance = 🎯 3.
Binary searching the largest possible minimum distance.
🐢 🐇
🧠
Never forget: Binary search distance d in [1 .. max−min]. canPlace(d) (greedy) true → save d, lo = d+1; else hi = d−1.
boolean canPlace(int[] s, int c, int d) {
  int count = 1, last = s[0];
  for (int i = 1; i < s.length; i++)
    if (s[i] - last >= d) { count++; last = s[i]; }
  return count >= c;
}
int aggressiveCows(int[] s, int c) {
  sort(s);
  int lo = 1, hi = s[s.length-1] - s[0], ans = 0;
  while (lo <= hi) {
    int mid = lo + (hi - lo) / 2;
    if (canPlace(s, c, mid)) { ans = mid; lo = mid + 1; }
    else hi = mid - 1;
  }
  return ans;
}

📚 Allocate the Books Minimize Max

Split books (in order) among S students so the student with the most pages reads as few as possible.

💡 The intuition (read this once, keep it forever)

Fair reading marathon: Hand contiguous piles of books to students. One unlucky student always gets the heaviest pile — you want to make that heaviest pile as light as possible. Guess a page-limit L: greedily give a student books until adding the next would exceed L, then start a new student. Did you fit within S students? If yes, tighten L; if no, loosen it.

The one insight: "can we finish with ≤ S students if nobody exceeds L pages?" is monotonic — a larger limit needs fewer students (FFF…TTT). So binary search the answer L between max(pages) and sum(pages). This is minimize-the-maximum — the twin of aggressive cows.

guess max-pages L→ greedily fill students up to L→ students used ≤ S? tighten (hi=L−1)/ else loosen (lo=L+1)
🔒 Lifetime takeaway: “Binary search the max pages; greedily split and ask ‘did it fit in S students?’”
Books [12,34,67,90], S = 2 students → minimum possible max-pages = 🎯 113.
Binary searching the smallest workable page limit.
🐢 🐇
🧠
Never forget: Search page-limit L in [max(pages) .. sum(pages)]. studentsNeeded(L) ≤ S → save + hi = L−1; else lo = L+1.
int studentsNeeded(int[] p, int limit) {
  int students = 1, pages = 0;
  for (int x : p) {
    if (pages + x > limit) { students++; pages = x; }
    else pages += x;
  }
  return students;
}
int allocateBooks(int[] p, int s) {
  int lo = max(p), hi = sum(p), ans = hi;
  while (lo <= hi) {
    int mid = lo + (hi - lo) / 2;
    if (studentsNeeded(p, mid) <= s) { ans = mid; hi = mid - 1; }
    else lo = mid + 1;
  }
  return ans;
}

🧠 Smallest Good Base Nested Search

For a number n, find the smallest base k in which n is written as all 1's (like 111).

💡 The intuition (read this once, keep it forever)

All-ones in disguise: "All 1's in base k with m digits" means n = 1 + k + k² + … + k^(m−1). More digits (bigger m) → smaller base. So loop m from large to small; the first base you find is the smallest. For each fixed m, the sum grows with k, so binary search the single base k that hits n exactly.

The two-layer insight: outer loop tries digit-count m from big (~60) down to 2 (more digits = smaller base = better). Inner binary search finds the base k because 1+k+…+k^(m−1) is strictly increasing in k — a clean monotonic target. First hit wins.

for m = high → 2→ binary search base k→ sum(k,m) == n? return k/ too big → smaller k, too small → bigger k
🔒 Lifetime takeaway: “Fix the digit-count, binary search the base; more digits = smaller base, so first hit is the answer.”
n = 13. With m = 3 digits, base 🎯 3 gives 1+3+9 = 13 = "111"₃.
For m=3 digits, binary searching base k so 1+k+k² = 13.
🐢 🐇
🧠
Never forget: Outer: digits m from big → small (first success = smallest base). Inner: binary search base k since Σ k^i is monotonic. Match → answer; overshoot → smaller k; undershoot → bigger k.
long smallestGoodBase(long n) {
  for (int m = 60; m >= 2; m--) {          // digits, big→small
    long lo = 2, hi = (long) pow(n, 1.0/(m-1)) + 1;
    while (lo <= hi) {
      long k = lo + (hi - lo) / 2, sum = 1, term = 1;
      for (int i = 1; i < m; i++) { term *= k; sum += term; }
      if (sum == n) return k;            // first hit = smallest base
      else if (sum < n) lo = k + 1;
      else hi = k - 1;
    }
  }
  return n - 1;                          // "11" in base n-1
}

🔤 Family of Strings — the K-th String Ordered Universe

All strings of length L over an alphabet, listed in dictionary order, form an ordered "family". Jump to the k-th one directly — binary search applied to an implicit sorted list.

💡 The intuition (read this once, keep it forever)

The odometer: Think of a car odometer with digits a, b, c instead of 0–9. Counting strings in dictionary order is just an odometer ticking. To reach the k-th reading you don't spin it k times — you divide: how many complete "blocks" of size base^(remaining) fit into k? That block index picks the current letter; the remainder picks the rest.

The one insight: the family is a sorted array you never build. Each letter position slices the remaining range into base equal blocks — choosing a letter is choosing which block, exactly like binary/n-ary search homing in on an index. This "search an implicit ordered space" is the deepest form of binary-search thinking.

block = base^(remaining positions)→ letter = k / block→ k = k % block→ repeat for next position
🔒 Lifetime takeaway: “An ordered family is an array you never build — divide by block size to land on the k-th directly.”
Alphabet {a,b,c}, length L=3 → 27 strings in order. Find the 🎯 k = 12-th (1-indexed) → "bac".
Choosing each letter by dividing the index into equal blocks.
🐢 🐇
🧠
Never forget: Work 0-indexed (k−1). For each position, block = base^(remaining); letter = k / block; then k %= block. It's positional number decoding.
String kthString(char[] alpha, int L, long k) {
  int base = alpha.length;
  k--;                               // to 0-indexed
  char[] res = new char[L];
  for (int pos = 0; pos < L; pos++) {
    long block = (long) pow(base, L - 1 - pos);
    res[pos] = alpha[(int)(k / block)];  // pick the block
    k %= block;                      // drop into that block
  }
  return new String(res);
}

🔑 Binary Search
O(log n) time · O(1)
Gotcha: use lo + (hi-lo)/2 to avoid overflow; decide <= vs < deliberately.
Follow-up: return the insertion index (lower_bound) when not found.
🎯 First & Last Occurrence
O(log n) time · O(1)
Gotcha: don't stop on a match — record it and keep moving toward the wanted edge.
Follow-up: count of a value = last − first + 1.
🔄 Rotated Sorted Array
O(log n) time · O(1)
Gotcha: duplicates (LC 81) break the "one half sorted" test → worst case O(n).
Follow-up: find the pivot / minimum of the rotated array.
⛰️ Peak Element
O(log n) time · O(1)
Gotcha: treat out-of-bounds neighbors as −∞; any peak is valid, not just the global max.
Follow-up: find a peak in a 2D grid (O(n log m)).
♻️ Repeated Element
O(n log n) BS · O(n) Floyd
Gotcha: if array is read-only & O(1) space, use Floyd's cycle (tortoise & hare) on a[i] as pointers.
Follow-up: why can't we just sort or hash? (space / mutation constraints).
🧩 Single Element
O(log n) time · O(1)
Gotcha: force mid even; relies on array being sorted with exactly one loner.
Follow-up: unsorted version → XOR all elements, O(n) O(1).
📈 Monotonic Predicate
O(log n · cost(check))
Gotcha: the check must be monotonic (FFF…TTT). Prove it before coding.
Follow-up: "binary search the answer" — recognise it in disguised problems.
√ Square Root
O(log n) time · O(1)
Gotcha: mid*mid overflows int → use long; return floor.
Follow-up: real-valued sqrt to precision ε (fixed ~100 iterations / Newton's method).
3️⃣ Kth Smallest (Array)
O(n log range) · O(n) avg quickselect
Gotcha: quickselect is O(n) average but O(n²) worst; value-BS is stable.
Follow-up: kth largest = (n−k+1)th smallest; heap gives O(n log k).
🔗 Kth in Two Sorted Arrays
O(log(min(n,m)))
Gotcha: binary search the shorter array; guard cuts with ±∞ sentinels.
Follow-up: median of two sorted arrays (LC 4) — same partition.
🔢 Kth in Sorted Matrix
O(n log range)
Gotcha: count ≤ mid with a bottom-left staircase (O(n)), not O(n²).
Follow-up: min-heap approach O(k log n); when is each better?
📈 Maximize K (answer search)
O(log range · check)
Gotcha: maximize → move right on success (last true); minimize → first true.
Follow-up: Koko eating bananas, ship-within-D-days (all this pattern).
🐄 Aggressive Cows
O(n log range) · sort O(n log n)
Gotcha: sort first; greedy feasibility check; it's maximize-the-minimum.
Follow-up: magnetic force between balls (LC 1552) — identical.
📚 Allocate Books
O(n log(sum))
Gotcha: lo = max(pages), not 0; splits must be contiguous; minimize-the-maximum.
Follow-up: split-array-largest-sum & painter's partition are the same.
🧠 Smallest Good Base
O(log²n)
Gotcha: iterate digit-count high→small; guard overflow in Σ kⁱ (early break).
Follow-up: why does base n−1 ("11") always work as fallback?
🔤 Family of Strings (k-th)
O(L)
Gotcha: convert to 0-indexed k−1; block = base^(remaining); watch overflow.
Follow-up: inverse — rank of a given string (positional encoding).
🌳 BST Search
