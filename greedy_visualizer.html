🪙 What is a Greedy Algorithm? local → global

A greedy algorithm builds a solution step by step, always taking the choice that looks best right now — never reconsidering. When the problem has the right structure, these local wins add up to the global optimum.

💡 Intuition

Grab the biggest coin: to make 63¢ with coins {25,10,5,1}, keep taking the largest coin that fits → 25,25,10,1,1,1 = 6 coins. It's optimal here because the coin system is "canonical". Greedy needs the greedy-choice property + optimal substructure; otherwise (e.g. coins {1,3,4} for 6) it can fail.
pick locally best→never undo→works if greedy-choice property holds

📅 Activity Selection I earliest finish

Given activities with start/finish times, pick the maximum number that don't overlap. Greedy rule: always take the activity that finishes earliest.

💡 Intuition

Free up the room soonest: sort by finish time. Pick the first; then repeatedly pick the next activity whose start ≥ the last chosen finish. Finishing early leaves the most room for future activities — provably optimal. Here → A, D, H, K (4 activities).
sort by finish time→take first→next start ≥ last finish? take it

⚖️ Activity Selection II — Why Finish Time? counterexamples

Other "obvious" greedy rules — earliest start, or shortest duration — fail. Watch a case where shortest-duration greedy loses to earliest-finish.

💡 Intuition

✅ Activity Selection III — N Meetings in a Room implementation

The classic interview form: given meeting start/end times, how many meetings can one room host? Same greedy, with the actual selection returned.

💡 Intuition

Track "last end": sort meetings by end time, keep a variable lastEnd = −∞. For each meeting, if its start > lastEnd, hold it and update lastEnd. Count how many you held. Here 6 meetings → 4 fit.
sort by end→if start > lastEnd: take & update→count = answer

🚉 Minimum Platforms I two-pointer sweep

Given train arrival & departure times, find the fewest platforms so no train waits. Sort both arrays and sweep with two pointers, tracking concurrent trains.

💡 Intuition

Count overlaps: sort arrivals and departures separately. Walk them in time order — an arrival before the next departure needs a new platform (count++); a departure frees one (count−−). The peak count is the answer. Here → 3 platforms.
sort arr[] & dep[]→arrival before departure? +1·else −1→track max

Never forget: on a tie (arrival == departure), process the departure only if the platform can truly be reused in time — otherwise count the arrival first.

🚦 Minimum Platforms II event / prefix sweep

A second view: turn every arrival into +1 and every departure into −1, sort all events by time, and take a running prefix sum. The maximum prefix is the answer.

💡 Intuition

Timeline of ±1: merge arrivals and departures into one chronological event list. Sweeping left to right, add +1 at each arrival and −1 at each departure; the running total is "trains currently in". Its peak is the platforms needed → 3. Same answer, event-driven framing.
events: +1 arrival, −1 departure→sort by time→running sum, track max

💼 Job Sequencing I deadline + profit

Each job takes 1 unit of time, has a deadline and a profit. Do at most one job per slot to maximize profit. Greedy: highest-profit jobs first, latest free slot.

💡 Intuition

Big money, late slot: sort jobs by profit descending. For each, place it in the latest free slot ≤ its deadline (leaving earlier slots open for tighter-deadline jobs). Skip if no slot fits. Here → jobs A, C, E for profit 142.

🔗 Job Sequencing II — DSU Speedup union-find slots

Finding the latest free slot naively is O(deadline). Union-Find makes it near O(1): each slot points to the next available slot to its left.

💡 Intuition

Jump to the free slot: a DSU parent array where find(d) returns the latest free slot ≤ d. After using a slot, union it to slot−1 so future queries skip straight past it. Profit-sorted jobs + DSU → same 142, but each placement is almost constant time.
find(deadline) = latest free slot→use it, union to slot−1→near O(1) each

🎒 Fractional Knapsack value/weight ratio

Fill a capacity-limited bag to maximize value, where items can be split. Greedy: take items by highest value-per-weight, splitting the last one to fill exactly.

💡 Intuition

Best bang per kg: sort items by value/weight ratio descending. Take whole items while they fit; when the next won't fully fit, take the fraction that does. Because splitting is allowed, this greedy is optimal (unlike 0/1 knapsack). Capacity 50 → value 240.
sort by value/weight ↓→take whole while it fits→take fraction of the last

📈 Kth Largest in a Running Stream size-k min-heap

As numbers stream in, keep the k largest in a min-heap of size k. Its root is always the kth largest so far — reportable in O(1) after each insert.

💡 Intuition

Guard the k biggest: a min-heap of size k holds the current top-k; the smallest of them (the root) is the kth largest. Push each new value; if the heap exceeds k, pop the min. Greedily discarding the smallest keeps exactly the k largest. Stream with k=3 → final kth largest = 8.
push value→size > k? pop min→root = kth largest
🔒 Keep forever: "Kth largest in a stream = size-k min-heap; the root is the answer at every step."

Never forget: "kth largest" → min-heap of size k; "kth smallest" → max-heap of size k. Keep the opposite extreme at the root.

🌳 Huffman Encoding I — Build the Tree min-heap merge

Optimal prefix codes: repeatedly merge the two least frequent nodes into a parent (their combined frequency). A min-heap surfaces the two smallest each time.

💡 Intuition

Rare letters, deep leaves: start with a leaf per character keyed by frequency. Pop the two smallest, join them under a new node (freq = sum), push it back. Repeat until one tree remains. Rare letters end up deep (long codes), frequent ones shallow (short codes). Freqs a5 b9 c12 d13 e16 f45 → root freq 100.
leaf per char (min-heap)→merge two smallest→push parent, repeat
🔒 Keep forever: "Huffman = greedily merge the two lowest-frequency nodes until one tree remains."

🧠
Never forget: Huffman is greedy and provably optimal — merging the two rarest first is guaranteed to minimize total code length.

🔤 Huffman Encoding II — Assign Codes traverse: 0 / 1

Walk the finished tree: going left appends 0, right appends 1. Each leaf's path is its codeword — no code is a prefix of another.

💡 Intuition

Path = code: DFS from the root; every leaf you reach gets the 0/1 string of the path taken. Frequent letters (shallow) get short codes, rare ones long. Total bits = Σ(freq × code length). For our tree → 224 bits (vs 288 for fixed 3-bit codes).
DFS the tree→left=0, right=1→leaf path = codeword
